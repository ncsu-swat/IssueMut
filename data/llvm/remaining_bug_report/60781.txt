Issue Title: __FLT_EVAL_METHOD__ is set to -1 with Ofast.
Original Post: On Linux, `math.h` includes this:
```h
/* Get __GLIBC_FLT_EVAL_METHOD.  */
#include <bits/flt-eval-method.h>

#ifdef __USE_ISOC99
/* Define the following typedefs.

    float_t	floating-point type at least as wide as `float' used
		to evaluate `float' expressions
    double_t	floating-point type at least as wide as `double' used
		to evaluate `double' expressions
*/
# if __GLIBC_FLT_EVAL_METHOD == 0 || __GLIBC_FLT_EVAL_METHOD == 16
typedef float float_t;
typedef double double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 1
typedef double float_t;
typedef double double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 2
typedef long double float_t;
typedef long double double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 32
typedef _Float32 float_t;
typedef double double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 33
typedef _Float32x float_t;
typedef _Float32x double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 64
typedef _Float64 float_t;
typedef _Float64 double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 65
typedef _Float64x float_t;
typedef _Float64x double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 128
typedef _Float128 float_t;
typedef _Float128 double_t;
# elif __GLIBC_FLT_EVAL_METHOD == 129
typedef _Float128x float_t;
typedef _Float128x double_t;
# else
#  error "Unknown __GLIBC_FLT_EVAL_METHOD"
# endif
#endif
```

`bits/flt-eval-method.h` is this:
```h
#ifdef __FLT_EVAL_METHOD__
# if __FLT_EVAL_METHOD__ == -1
#  define __GLIBC_FLT_EVAL_METHOD	2
# else
#  define __GLIBC_FLT_EVAL_METHOD	__FLT_EVAL_METHOD__
# endif
#elif defined __x86_64__
# define __GLIBC_FLT_EVAL_METHOD	0
#else
# define __GLIBC_FLT_EVAL_METHOD	2
#endif
```

After https://reviews.llvm.org/D109239 with Clang with `-Ofast`, `__FLT_EVAL_METHOD__` gets a value of -1, meaning it is set by that to 2 and we end up using long double for `float_t` and `double_t`. 
https://godbolt.org/z/PqsxrxYqn

From the comments in D109239 it doesn't appear it was expected to be used in this way. It created an ABI break for `float_t` and `double_t` types, along with using the very inefficient long double types on some architectures.

Comment by kito-cheng: Just remind that you posted the x86's `bits/flt-eval-method.h`, the generic one has more comment about why it mapping -1 to 2.

https://github.com/bminor/glibc/blob/master/bits/flt-eval-method.h#L23
```c
/* __GLIBC_FLT_EVAL_METHOD is the value of FLT_EVAL_METHOD used to
   determine the evaluation method typedefs such as float_t and
   double_t.  It must be a value from C11 or TS 18661-3:2015, and not
   -1.  */

/* In the default version of this header, follow __FLT_EVAL_METHOD__.
   -1 is mapped to 2 (considering evaluation as long double to be a
   conservatively safe assumption), and if __FLT_EVAL_METHOD__ is not
   defined then assume there is no excess precision and use the value
   0.  */

#ifdef __FLT_EVAL_METHOD__
# if __FLT_EVAL_METHOD__ == -1
#  define __GLIBC_FLT_EVAL_METHOD	2
# else
#  define __GLIBC_FLT_EVAL_METHOD	__FLT_EVAL_METHOD__
# endif
#else
# define __GLIBC_FLT_EVAL_METHOD	0
#endif
```

Comment by davemgreen: There are some comments in https://reviews.llvm.org/D109239 explaining the reasoning too. I think with hindsight that might have been the wrong way to go though.

Please correct me if any of this is wrong but:
 - In practice on linux systems out there in the wild, for better or worse, they use `__FLT_EVAL_METHOD__` to control the type of float_t and double_t. With `__FLT_EVAL_METHOD__==-1` they use `__FLT_EVAL_METHOD__=2`.
 - `__FLT_EVAL_METHOD__` will be -1 on -Ofast, but 0 on other optimization levels.
 - So we end up with -Ofast and -O3 causing float_t and double_t to have different types. This creates an abi incompatibility between code compiled with Ofast and O3. https://godbolt.org/z/b3c47aq15

The code in math.h might want to be changed, but that doesn't fix the existing systems. I'm not sure how common it is to use float_t and double_t on an ABI boundary. It sounds like it would be a bad idea in any case. But if that is done then clang/llvm will currently be causing problems on any existing system.

I am not strongly opinionated about it, and I've not heard reports from users even though clang-15 has been out for a while, but it would seem that with the uses in math.h that setting `__FLT_EVAL_METHOD__` to 0 by default might be the better option, even for Ofast.

Comment by Wilco1: That review confuses optimization, precision and accuracy. Optimization changes the expressions evaluated. While that might give more or less accurate results, it still uses the same precision for the evaluation (ie. float or double operations on most targets). The C/C++ standards explicitly state the FMA optimization (which changes accuracy of the evaluation) as _not_ affecting FLT_EVAL_METHOD.

So FLT_EVAL_METHOD is about the precision of evaluation, not about accuracy changes resulting from optimization.

Given this change breaks several C libraries (as mentioned in D121122), it should really be reverted.
