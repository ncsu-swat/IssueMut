Issue Title: Incorrect -Wformat type warnings with non-variadic functions
Original Post: This piece of code produces an incorrect warning when compiled with `-Wformat`: 
```cpp
template <typename... Args>
__attribute__((__format__(__printf__, 1, 2)))
void my_format(char const *format, Args... args);

void foo()
{
	float x = 0.f;

	my_format("%f", x);
}
```
```console
<source>:9:18: warning: format specifies type 'double' but the argument has type 'float' [-Wformat]
        my_format("%f", x);
                   ~~   ^
                   %f
```
Meanwhile, declaring `my_format` as a variadic function results in no warning, as expected:
```cpp
__attribute__((__format__(__printf__, 1, 2)))
void my_format(char const *format, ...);

void foo()
{
	float x = 0.f;

	my_format("%f", x);
}
```
It doesn't seem to be related to `my_format` being templated, declaring it as `void my_format(char const *format, float f);` results in the same incorrect warning.

Comment by JoyNyuguto:  @sapphyrus @SamTebbs33 Joy Nyuguto Outreachy
The warning occurs because the format specifier "%f" is intended for double-precision floating-point values but the argument passed to my_format is a single-precision floating-point value of type float. 

To resolve the warning in the templated version of my_format, you can explicitly cast the float argument to double:
my_format("%f", static_cast<double>(x));
``

Alternatively, you can use a different format specifier that is intended for single-precision floating-point values, such as "%g" or "%.f"

``my_format("%g", x);
``my_format("%.f", x);
In both cases, the warning should no longer be triggered because the format specifier matches the type of the argument.

With some experience with this case in Chromium, I think this diagnostic is unhelpful and should likely be suppressed in this case.

If the implementation forwards the supplied args to a variadic method like printf, default argument promotion will happen and the warning will be moot. If it does not, then the argument types are available to it from the function declaration (e.g. in a parameter pack) and it will not erroneously read extra bytes from memory or the like. Either way, the problem the warning intends to prevent -- that the caller has supplied a value that will be fundamentally misinterpreted by whatever deals with the format string -- isn't occurring.

I think this warning should be suppressed in the case where, if default argument promotion had been applied, the argument type would match the expected type.

Comment by AaronBallman: Strictly speaking, the diagnostic is correct -- C specifies that `%f` receives a `double`, this is passing a `float` and a `float` is not a `double`. If the user is using `printf` format specifiers because they're passing the data along to `printf` (or similar), then I agree the diagnostic is bad. But the attribute is saying it's using `printf`'s format specifiers, not that the data will eventually be passed to `printf`. Comment by apple-fcloutier: It's important context that it was impossible to use `__attribute__((format))` on non-variadic functions (including C++ variadic template functions) until I submitted a patch to make it work last year. This means previously, any function using `__attribute__((format))` (including an eventual function copying a `double` to a serial bus) was variadic, and when it was passed a `float`, it actually received a `double` because C specifies that floats are promoted to doubles when passed as variadic arguments.

You're right that preciously few people use `__attribute__((format))` on variadic template functions, but again, that's mostly because it wasn't possible at all before last year, and this issue is a deterrent to more widespread use. We know this because the case before us is that Chrome wants to adopt it but won't unless we fix this.

I think that the question we should try to answer is: in that ~year since `__attribute__((format))` can apply to functions with fixed arguments, has anyone leveraged incompatibilities with `float` types? I don't see how that could be the case, because as it stands, it simply means that fixed-parameter functions with `__attribute__((format))` cannot have parameters with types that variadic argument promotion never produces, such as `float`, `char` and `short`. If no one has leveraged incompatibilities in this way, is there still an argument to leave it the way it is?

Comment by AaronBallman: I think there's at least two different angles being discussed:

One seems to be: this is a false positive if you're passing the arguments along to `printf`; the ability to use the `format` attribute on a variadic function is ~1 year old, so there's not a lot of code relying on the existing behavior, so we've probably got the ability to change the diagnostic behavior without surprising a lot of users and that removes a false positive.

Another is: what do people expect the attribute to do? Our [documentation](https://clang.llvm.org/docs/AttributeReference.html#format) says: "As an extension to GCC’s behavior, Clang accepts the format attribute on non-variadic functions. Clang checks non-variadic format functions for the same classes of issues that can be found on variadic functions, as controlled by the same warning flags, except that the types of formatted arguments is forced by the function signature." -- that reads to me like this attribute behaves exactly the same as the variadic case, except the types come directly from the function signature rather than the expressions passed as arguments to the function; there are situations where that behavior is useful.

I view the first as being "can we make the change?" and the second as being "should we make the change?" I suspect we can make the change (I don't think it would be overly disruptive), but I'm less convinced we should make the change given that there are reasonable use cases where the type from the function signature not matching the type in the format specifier can be a problem. Changing the diagnostic to assume promotion happens prevents useful diagnostics in some circumstances while silencing unhelpful false positives in others.

I think an underlying question here is whether use of the `format` attribute implies passing the arguments along to the specified function or not. On the one hand, I don't think we want it to imply that because that limits the utility of the attribute. It is reasonable to use format specifiers without passing them along to the specified function given how ubiquitous the format specifiers are. On the other hand, how often do people implement the *full set of format specifiers* for e.g., `printf` but then not turn around and pass the argument on to a printf-variant?

I'm not certain there's a "clearly correct" answer here.

It's worth noting that the original example code has a trivial fix to silence the diagnostic: https://godbolt.org/z/edKzWoWzz Because the format function takes a parameter pack, you can pass the correct type (or use a cast, etc) for the given format specifier and all is well. So the truly problematic case is not with packs, it's with functions with an explicit parameter of a promotable type, which is perhaps a bit of a "doctor, doctor, it hurts when I do this" kind of situation.
