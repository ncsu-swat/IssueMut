Comment by Sirraide: @AaronBallman Is this valid in C23? The problem here is the division by zero. We’re hitting a code path in codegen in `VarDecl::evaluateValueImpl` where we check for `IsConstantInitialization && (Ctx.getLangOpts().CPlusPlus || Ctx.getLangOpts().C23)`, and if that is the case and we emitted any notes, constant evaluation fails, and as a result, codegen issues this error.

This entire situation seems odd to me. From what I can tell, this check also fails for C++, but ostensibly, it still manages to constant-initialise the variable through some other means. Replacing `Ctx.getLangOpts().C23` with `(isConstexpr() && Ctx.getLangOpts().C23)` ‘fixes’ the problem, but this seems more like fixing symptoms rahter than the underlying cause...
Comment by Sirraide: In other words, it seems like codegen for C is more or less treating global `const` variables as though they were `constexpr`.
Comment by gustedt: For the status of this in C23 and before, my understanding is that if `FE_DIVBYZERO` exists a floating division by zero that is evaluated at execution time raises this exception and if `INFINITY` exists the result of the operation should be exactly that. Now, if such an expression is evaluated at compile time, the result should be the same, but not flag should be raised at runtime. 

Whether or not anything changes for C23's `constexpr` should be irrelevant, here, this part of the standard did not change for other static variables.

And in any case, this is a regression, it worked previously and doesn't work now. If such a regression is intended, it should at least be documented.

Comment by AaronBallman: 6.7.11p5: "All the expressions in an initializer for an object that has static or thread storage duration or is declared with the constexpr storage-class specifier shall be constant expressions or string literals."

6.6p4: "Each constant expression shall evaluate to a constant that is in the range of representable values for its type."

6.6p17: "The semantic rules for the evaluation of a constant expression are the same as for nonconstant expressions."

F.2.2p1: "Since negative and positive infinity are representable in ISO/IEC 60559 formats, all real numbers lie within the range of representable values."

F.8.5p: "An arithmetic constant expression of floating type, other than one in an initializer for an object that has static or thread storage duration or that is declared with storage-class specifier constexpr, is evaluated (as if) during execution; thus, it is affected by any operative floating-point control modes and raises floating-point exceptions as required by ISO/IEC 60559 (provided the state for the FENV_ACCESS pragma is "on")."

F.8.6p1: "All computation for automatic initialization is done (as if) at execution time; thus, it is affected by any operative modes and raises floating-point exceptions as required by ISO/IEC 60559 (provided the state for the FENV_ACCESS pragma is "on"). All computation for initialization of objects that have static or thread storage duration, or that are declared with storage-class specifier constexpr, is done (as if) at translation time."

(We aim for conformance to Annex F though how conforming we are to it is still a question mark.)

So yes, I agree with @gustedt that this code should be accepted. This regressed on trunk: https://godbolt.org/z/jxa7z64nx
