Issue Title: Potential regression in AST printing
Original Post: https://github.com/llvm/llvm-project/commit/46f3ade5083b8bfce55c78a21086a487eaac6f99 intends to fix the printing of attributes attached to variable declarations. The implementation choice is to print the attributes on the left hand side. However, that forces that change drifts away the produced output from the output as written in the code. This is also evident from the tests the commit had to change.

Consider,
```cpp
void f() __attribute__((always_inline)) {}
```

`clang-17 -Xclang -ast-print` produces `void f() __attribute__((always_inline)) {}` which matches very closely the original code. However, `clang-18 -Xclang -ast-print` produces `__attribute__((always_inline)) void f() {}`

Both compile but I think the second one violates a principle which I believe we have been following where we try to produce output close as much as possible to the user code.

@giulianobelinassi, @erichkeane  do you think we can bring the old behavior back before freezing 18 by limiting that feature to variable declarations only? This was the original intent of the patch IIUC.

@alexander-penev, @AaronBallman.

Comment by giulianobelinassi: The reason why this attribute is printed on the left side is because for us it is critical that the functions are also compilable with `gcc`, and it rejects attributes on the right side of a function that is declared with its body. The reason for that is a potential ambiguity when handling K&R C functions.
```
f(i) __attribute__((unused)) int i; {}
```
In this case it is not clear where the attribute should be applied and therefore GCC rejects all declarations of this kind. This is used when generating a Kernel Livepatch thus I'd like this behaviour to be maintained while fixing the `override` keyword.

Comment by AaronBallman: > I’m not sure this whether this is really a regression or just a breaking change. CC @AaronBallman

It's a bit of both. We intentionally changed where we print attributes and that could break code relying on previous printing locations, but the intent was to get attributes to print in a more regular location (previous behavior would lead to broken code as well, but in more circumstances). That said, the goal of `-ast-print` is to get back to the user's original source code as close as we can, so it's also a bit of a regression.

> Would it make sense to take a different approach here and set a bit in the attribute class telling us where the attribute occurred? In that the printer would not have to deal with ambiguities as it does not have enough information to do so. The advantage of that approach is that in case you wanted to "fix" GCC-incompatible code, the tool can flip that bit of the attribute and be done with it...

I think that still leads to issues, but hopefully we could work around them. Consider something like:
```
[[clang::foo]] __declspec(something) __attribute__((baz)) int x [[clang::bar]] () [[clang::quux]] __attribute__((another_one));
```
A bit in the attribute class doesn't really tell you enough, because that's a valid declaration (https://godbolt.org/z/oPTE4c89a) while reordering the attributes a bit causes it to be an invalid declaration (https://godbolt.org/z/jMn78dhnh).

We'd need to track locations like: start of line, after identifier, after parameter list, after lambda introducer, etc as well as tracking attribute order within each location.

> But again: we don't need to "fix" non-gcc compatible code.

The request is also to fix standards conforming code: https://godbolt.org/z/hYnWTz5nn
