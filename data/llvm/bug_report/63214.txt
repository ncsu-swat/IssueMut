```cpp
void name(int *params, int *program, int r, int g, int b, int a) {
  auto fn = (void (*)(int *, int *, int, int, int, int))1;
```

```shell

```

Comment by nemanjai: This seems to be a poorly thought-out attribute. We ultimately can't tail-call across DSO boundaries. Comment by efriedma-quic: In case anyone else is confused why this isn't possible, the issue isn't actually the existence of TOC.  The problem comes when you have "a" and "b" with the same TOC, and "c" with a different TOC.  "a" calls "b", which musttail calls "c".  When "a" calls "b", the linker sees they have the same TOC, so "a" doesn't have any code to save/restore the TOC.  But a musttail call to "c" modifies the TOC, and nothing restores it.  So that isn't legal.

The solution here is pretty simple: you add a marking to "b" that tells the linker not to do this optimization on calls to "b".  As far as I can tell, that marking actually does exist... but only for the ELFv2 ABI.
Comment by nemanjai: Right. So a couple of notes:
1. Converting a `musttail` call to a normal call is probably wrong. Its name includes the word `must` so we must honour it or diagnose it and reject the compilation.
2. This attribute *can* be honoured as Eli points out. Any function that has a `musttail` call to an external function (for which we don't know if it shares the same TOC pointer) needs to have its `st_other` field set to `1` (i.e. "clobbers TOC, treat as caller-saved"). And yes, this is an ELFv2 ABI-specific fix. This will tell the linker to treat calls correctly for this function (see next point for the compiler).
3. The compiler needs to learn to emit the `call+nop` calls when the callee has `musttail` calls (i.e. such a function must return `false` from `callsShareTOCBase()` for any caller).
4. An equivalent mechanism to the `st_other` field needs to be found for ELFv1.
