Issue Title: [analyzer] Many duplicated ArrayBoundV2 reports
Original Post: Recently I had a look at the diff what a clang-18 upgrade would bring, and it turns out we have some inflation in terms of ArrayBoundV2 bug reports.

 When I looked at the cases, I started wondering how useful the new "duplicates" are, and I think they are not too relevant.
Here is an example to illustrate the case:
https://godbolt.org/z/jozGzj9zv
```c++
[[noreturn]] void myabort(); 

int rng();
int getIndex() {
  switch (rng()) {
    case 1: return -152;
    case 2: return -160;
    case 3: return -168;
    default: myabort();
  }
}

void top(char *p, int n) {
  char arr[100];
  p = arr;
  while (rng()) {
    p[getIndex()] = 10; // 3 warnings: Out of bound access to memory preceding 'arr'
  }
}
```

I've seen the pattern multiple times, that we have an expression for which we raise the same exact issue, but with a different index in the note. I'd argue that fixing one of these would fix the rest too, thus raising this multiple times for different indexes is questionable.

This isn't an issue that I see frequently, but I think the "uniqueing location" is for solving this/similar situations.

@NagyDonat Have you seen patterns like this? Do you agree that we should unique these reports?

Comment by NagyDonat: Good question, I'm summarizing my immediate thoughts below (feel free to continue the discussion if you feel that I didn't cover something or you have other ideas).

The difficulty is that in the individual reports the analyzer will show concrete details (e.g. reports the concrete index in notes) that are specific to that particular report. (As a wild guess I'd say that the report numbers are inflated now because the checker reports more details and the previously identical "out of bounds access here" reports became distinct.)

I feel that in the path-sensitive paradigm the "natural" behavior is to report these findings separately. Merging/discarding findings with a uniqueing location is a "dirty" operation: it handles the finalized report as immutable objects and makes the remaining reports inaccurate in the sense that they'll emphasize specific details that are not representative for the whole merged group.

This could lead to ugly whack-a-mole situations in certain cases when e.g. there are many bug paths that all produce out-of-bounds access in the same location (e.g. the element access method of a custom vector class) -- the checker reports just a single bug, the user whacks it, the checker reports a second bug etc.

Adding a uniqueing location could have been the "least evil" solution if this issue produced truly unacceptable amounts of spam, but IMO it's still an "evil" solution that hides and obfuscates the true behavior of the checker, so I'd prefer to avoid implementing it.

By the way, I think that in your concrete example the "right" (and very difficult) solution would've been that we recognize that these three branches of the exploded graph just differ in the value of one single location and unify them into a single branch where the value is symbolic with three potential values.

Implementing this would be prohibitively complex in the current architecture where `nonloc::ConcreteInt` is completely separated from a `nonloc::SymbolVal` with a few possible values, but if concrete integers were symbolic values with an 1-element range, then we could perform a check that merges sibling branches where the states only differ in constraints about one single symbol. There would be difficulties even in that case (e.g. bug path visitors don't understand state merges and they would still report inaccurate things), so this is a "nice to think about, won't be implemented" remark.

Comment by Xazax-hun: This is a tough question. On one hand we do not want to flood our users with duplicate warnings, on the other hand, if we happen to pick the wrong representative (that happens to be on an infeasible path) after the uniqueing process, the user might dismiss a legitimate error. 

I think this might be a UI problem. I wish we had a UI that would show warnings like these grouped. That being said, I think the same problem could happen with other existing checks, like memory leaks. We just pick one of the paths where the memory was leaked, and it might be an infeasible path. So, existing practice in the analyzer seems to suggest that we prefer to do the uniqueing. This makes me slightly biased towards that for the sake of consistency.

Comment by NagyDonat: I agree with @haoNoQ that:
> I think this might be a UI problem. I wish we had a UI that would show warnings like these grouped.

Deduplication (keep one and discard the rest) is a good solution when the reports are completely equivalent and the duplication is only caused by technical details. If the reports are similar, but not identical (each of them provides some new information), then the core/backend should return them all and the frontend/UI layers should handle them as an collapsible/expandable group.

I could accept something like `--agressively-deduplicate` or `--discard-similar-reports` that reduces these groups to a single element (for situations where there isn't a separate frontend or it doesn't support grouped display). However, I think this should be off-by-default, because the "silently discard similar reports" behavior is counter-intuitive and hard to notice; while "too many similar reports" is a visible situation that can be handled by activating a flag (if the UI is not good enough to provide a "best of both" solution).

Comment by NagyDonat: I thought about this issue and I think I can resolve it. My rough plan is that:
1. I will introduce `ArrayBoundBugReport` as a subclass of `PathSensitiveBugReport` which has a custom `Profile` method and ensures that these very similar reports are sorted into the same report equivalence class.
2. I'll add a noop-by-default virtual method `selectedAsRepresentative()` to the base class `BugReport` and ensure that it is called when a certain bug report is selected as the representative of a bug report equivalence class.
3. Define `ArrayBoundBugReport::selectedAsRepresentative()` to
   - remove the specific negative byte offset value from the long message of the bug report, which looks like "Access of <region> at negative byte offset -123" (because different bug reports will have different numbers, so the "representative" cannot represent them all in this aspect)
   - add a note like "this issue is also reached through 77 other code paths".

This way we can display the exact (and potentially helpful) information in the common case when the report doesn't have "clones", but we don't display inaccurate (too specific) information in the case when we have to summarize a family of similar (but not identical) reports.

I think I can implement this in a reasonably generic way that can be potentially reused in other checkers that may produce similar issues in the future.
