Comment by KanRobert: @GabrielRavier APX is not supported in 32-bit mode. We may report the error in a more elegant way.
Comment by phoebewang: Should we make it compiler successfully even with APX feature? I think it's common when user uses `-m32 -march=native` or the IR generated from other frontends.
Comment by KanRobert: > Should we make it compiler successfully even with APX feature? I think it's common when user uses `-m32 -march=native` or the IR generated from other frontends.

Yes, sounds reasonable.
Comment by FreddyLeaf: gcc reported such error: https://godbolt.org/z/zar7aPen3
error: '-mapxf' is not supported for 32-bit code
Comment by KanRobert: > gcc reported such error: https://godbolt.org/z/zar7aPen3 error: '-mapxf' is not supported for 32-bit code

My thought is that user is trying to enable all the possible feature in 32-bit mode on current machine when passing "-march=native -m32". He/She does not need to know the feature dependencies. 

Reporting an error does not make sense to me. I will talk to GCC developers about this.
Comment by KanRobert: Talked to GCC folks.  Compiler should not emit APX instructions for `-m32 -mapxf` and should not report any warning/error. Instead, we will add documentation somewhere to say that `apxf` is not supported in 32-bit mode. Similarly  for `usermsr, uintr, amx`. 

The first proposal is to add the doc in the help info of `-m32`. @phoebewang Better idea?


Comment by phoebewang: I think you can add it here https://clang.llvm.org/docs/UsersManual.html#x86
Comment by KanRobert:  HJ proposed a new behavior for -mapxf and other 64-bit only features

a. Error for `-mapxf -m32` would error
b. No error for `-march=native -m32` and disable 64-bit features silently
	
https://gcc.gnu.org/bugzilla/show_bug.cgi?id=115978

Now GCC detects `-mapxf` and `-muintr` https://gcc.gnu.org/bugzilla/attachment.cgi?id=58698&action=diff
