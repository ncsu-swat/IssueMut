Issue Title: [clang] False-positive with -Wswitch-default and templates
Original Post: Compiling the following code with Clang trunk and ` -Wswitch-default` option produces "'switch' missing 'default' label" warning, despite the label clearly being there:

```cpp
template<typename Index>
int f1(Index i)
{
    switch (i)
    {
        case 0: return 0;
        case 1: return 1;
        default: return 2;
    }
}
```

```console
$ clang++ -fsyntax-only -Wswitch-default test.cpp 
test.cpp:4:5: warning: 'switch' missing 'default' label [-Wswitch-default]
    4 |     switch (i)
      |     ^
1 warning generated.
```

Comment by aaronpuchert: I think the problem is the loop condition `SC && !HasDependentValue`. We also don't emit an error on duplicate default labels, which should violate [[stmt.switch]p3](https://eel.is/c++draft/stmt.switch#3):
```c++
template<typename Index>
int f1(Index i)
{
    switch (i)
    {
        case 0: return 0;
        case 1: return 1;
        default: return 2;
        default: return 3;
    }

```
For what it's worth, GCC and MSVC also don't produce an error here. It's also rather strange code: if the type that we switch on is a template parameter, how can the values be fixed?

Comment by al42and: >  It's also rather strange code: if the type that we switch on is a template parameter, how can the values be fixed?

In the original code, this function is used exclusively with integral types. They are assumed to have a limited range of values, but can be either `int` or `size_t`, and we wanted to avoid any spurious type conversions. This is likely unnecessary, since all the relevant code is in the same translation unit and the optimizer can see through, but it was done while dealing with a GPU register allocator issue, and I was too lazy to also check how well integer widening/narrowing would be handled here; and that's how this code came to be. But I think such pattern can have other uses (also limited to integral types), e.g., returning known values for small inputs and falling back to `default: return slow_function<T>(x);` otherwise, so the code snippet should not be totally nonsensical.
